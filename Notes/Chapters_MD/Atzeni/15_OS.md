## Introduction

Operating system forensics analyzes the artifacts produced, stored, and mediated by an operating system. It bridges file-system forensics, log analysis, process analysis, memory forensics, and network evidence.

The OS is often the layer where user actions, application behavior, hardware resources, and security events become observable.

---

## 1. OS-Level Evidence Sources

> 📎 *Slide reference: `15_OS.pdf` — Operating System Forensics*

Important OS-level sources include:
- file and directory structures;
- allocated and unallocated storage;
- registries and configuration files;
- event logs;
- user histories;
- connected-device traces;
- process and kernel state;
- memory dumps.

On Windows, examples include Event Viewer, Prefetch files, and LNK files. On Unix-like systems, examples include shell histories, `/var/log/auth.log`, system logs, and `/proc`.

---

## 2. Rootkit Investigation

Rootkits are especially relevant because they often operate at kernel level and try to hide their own presence.

A rootkit investigation should cross-check:
- centralized logs;
- missing or inconsistent log sequences;
- kernel messages and modules;
- system calls;
- process lists and process metadata;
- memory contents;
- network sockets and traffic.

No single view is sufficient. A rootkit can tamper with one source, so the examiner looks for contradictions between independent sources.

---

## 3. Process and Kernel Analysis

Process analysis includes ordinary tools such as `ps`, `top`, and procfs on Unix-like systems, but the forensic point is not merely to list processes. The examiner must identify anomalies:
- processes without plausible parents;
- unusual runtime, CPU, or memory behavior;
- path mismatches;
- hidden or unlinked processes;
- unexpected system-call behavior.

Tools such as `strace` and `sysdig` can help observe interactions with the operating system, but live observation must be treated carefully because it changes the running system.

---

## 4. Network and Socket Evidence

Rootkits and malware often communicate with command-and-control infrastructure, exfiltrate data, or listen for inbound commands.

Local socket tools such as `netstat`, `ss`, and `lsof` can reveal active or listening connections. Network captures through tools such as Wireshark, tcpdump, or Zeek can complement host evidence.

The strongest analysis correlates:
- the owning process;
- local and remote endpoints;
- timestamps;
- DNS or proxy logs;
- malware or threat-intelligence indicators.

---

## 5. Link to Memory Forensics

Atzeni presents memory analysis as the deeper layer when OS-level artifacts may be incomplete or manipulated. Fileless malware may avoid writing to disk, and encrypted malware may hide its persistent body, but runtime behavior still requires memory.

This makes RAM a critical source for:
- decrypted payloads;
- credentials and keys;
- active process state;
- injected code;
- open files and handles.

---

## Key Concepts & Definitions

| Term | Definition |
|------|------------|
| **OS Forensics** | Forensic analysis of operating-system artifacts and runtime state. |
| **Rootkit** | Malware designed to hide itself, often by manipulating kernel or OS structures. |
| **Prefetch** | Windows artifact indicating program execution behavior. |
| **LNK File** | Windows shortcut artifact that may reveal accessed files or paths. |
| **procfs** | Unix-like virtual filesystem exposing process and kernel information. |

---

## Summary
- OS forensics connects storage, logs, processes, network activity, and memory.
- Rootkit investigations require cross-source consistency checks.
- Missing logs can be evidence of tampering.
- Process anomalies and socket activity are important indicators.
- Memory forensics extends OS forensics when ordinary artifacts are hidden or incomplete.
