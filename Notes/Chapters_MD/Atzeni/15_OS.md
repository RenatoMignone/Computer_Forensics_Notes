## Introduction

This chapter covers operating-system forensics and the acquisition side of volatile memory forensics. The correction applied here is important: the material previously stored as Chapter 16 belonged to the second part of Chapter 15. The real Chapter 16 begins with the detailed Volatility analysis workflow developed in Lecture 30.

Operating-system forensics bridges file-system artifacts, logs, process state, kernel behaviour, network sockets, and RAM acquisition. The OS is where user actions, application execution, storage, memory, and network activity become observable.

---

## 1. OS-Level Evidence Sources

> 📎 *Slide reference: `15_OS.pdf` — Operating System Forensics*

Important OS-level sources include:
- file and directory structures;
- allocated and unallocated storage;
- registries and configuration files;
- event logs;
- user histories;
- connected-device traces;
- process and kernel state;
- memory dumps.

On Windows, examples include Event Viewer, Prefetch files, and LNK files. On Unix-like systems, examples include shell histories, `syslog`, `/var/log/auth.log`, kernel messages through `dmesg`, and `/proc`.

---

## 2. Rootkit Investigation

Rootkits are especially relevant because they often operate at kernel level and try to hide their own presence.

A rootkit investigation should cross-check:
- centralized logs such as `syslog` or Windows Event Viewer;
- missing or inconsistent log sequences;
- kernel messages and modules;
- system calls;
- process lists and process metadata;
- memory contents;
- network sockets and traffic.

No single view is sufficient. A rootkit can tamper with one source, so the examiner looks for contradictions between independent sources.

---

## 3. Process, Kernel, and Socket Analysis

Process analysis includes ordinary process listings, kernel/process statistics, and procfs-style views on Unix-like systems. The forensic point is not merely to list processes, but to identify anomalies:
- processes without plausible parents;
- unusual runtime, CPU, or memory behaviour;
- path mismatches;
- inconsistent process relationships or data structures;
- unexpected system-call behaviour.

Local socket tools such as `netstat`, `ss`, and `lsof` can reveal active or listening connections. Network traffic acquisition can complement host evidence when local OS views are incomplete or manipulated.

The strongest analysis correlates the owning process, local and remote endpoints, timestamps, DNS or proxy logs, and malware or threat-intelligence indicators.

---

## 4. Why Memory Acquisition Matters

> 📎 *Slide reference: `15_OS.pdf` — Volatile memory acquisition*

Atzeni presents memory acquisition as the deeper layer when OS-level artifacts may be incomplete or manipulated. Fileless malware may avoid writing to disk, and encrypted malware may hide its persistent body, but runtime behaviour still requires memory.

RAM can contain:
- decrypted payloads;
- credentials and keys;
- active process state;
- injected code;
- open files and handles;
- active network connections.

---

## 5. Debugging Tools, Crash Dumps, and Forensic Limits

Many tools can inspect memory, but not all are suitable as forensic acquisition tools. Debuggers such as `gdb` can inspect or stop processes and capture limited memory areas, but they are designed for development and troubleshooting.

For forensic use, they may be challenged because:
- they modify the running system;
- they provide partial access;
- they may not be certified or robust for evidentiary use;
- they do not necessarily preserve a full, repeatable snapshot.

Crash dumps can preserve useful state, but they are also primarily debugging artifacts and may not satisfy the needs of a complete forensic investigation.

---

## 6. Memory Dumps

> 📎 *Slide reference: `15_OS.pdf` — Memory dump*

A memory dump is a point-in-time capture of RAM. It may contain process state, open files, network connections, decrypted data, and traces of malware.

The acquisition is delicate because RAM changes continuously. Installing and running an acquisition tool can itself modify memory. This must be documented because it can be challenged in court.

---

## 7. Acquisition Tools

Atzeni discusses several acquisition approaches:
- **LiME**, a Linux kernel module for live memory extraction;
- **Fmem**, which exposes physical memory as a raw device file;
- **AVML**, which can acquire memory and transfer it to local or remote destinations;
- crash dump tools such as `kdump`, which are primarily designed for debugging but may preserve useful forensic state.

The investigator should prefer tools and workflows that reduce interaction with the target system and immediately preserve integrity through hashing and documented transfer.

---

## 8. LiME

> 📎 *Slide reference: `15_OS.pdf` — LiME*

LiME can acquire the full contents of Linux RAM and save it locally or stream it over the network. Network streaming can be useful because it avoids writing large evidence files onto the target disk.

LiME must be compiled for the target kernel and architecture. This is not cosmetic: memory structures depend on the exact operating-system version, so a mismatch can prevent correct acquisition or later analysis.

## Key Concepts & Definitions

| Term | Definition |
|------|------------|
| **OS Forensics** | Forensic analysis of operating-system artifacts and runtime state. |
| **Rootkit** | Malware designed to hide itself, often by manipulating kernel or OS structures. |
| **Prefetch** | Windows artifact indicating program execution behaviour. |
| **LNK File** | Windows shortcut artifact that may reveal accessed files or paths. |
| **procfs** | Unix-like virtual filesystem exposing process and kernel information. |
| **Memory Dump** | Snapshot of RAM acquired for later analysis. |
| **LiME** | Linux Memory Extractor, used for live memory acquisition. |
| **AVML** | Linux memory acquisition tool mentioned as an alternative acquisition path. |

## Summary
- Chapter 15 now includes the old Chapter 16 acquisition material because it belongs to OS and memory-acquisition foundations.
- OS forensics connects storage, logs, processes, network activity, and memory.
- Rootkit investigations require cross-source consistency checks.
- Missing logs and inconsistent process views can indicate tampering.
- Memory acquisition is necessary when ordinary OS artifacts are hidden, incomplete, or manipulated.
- Debuggers and crash dumps may help but are not substitutes for a forensic RAM snapshot.
- LiME, Fmem, AVML, and crash dumps represent different acquisition paths.
- Acquisition must be fast, documented, minimally invasive, and integrity-preserving.
